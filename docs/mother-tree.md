# TxtVein · 母树 / 子树架构规范

> 状态：**v0.1 设计定稿，尚未接线**。
> 这份文档定义数据模型与不变量；当前代码仍使用单一 `dict.tv`。
> 实现顺序见 [`../NEXT.md`](../NEXT.md)。

---

## 一、一句话

**公共母树提供世界的共识，私人子树承载私人的真相。**

母树是只读的标准会计学与通用商户分类；子树是用户自己的节点、简码、别名与归属选择。
子树通过稳定的 `anchor_id` 挂到母树，而不是复制母树的文字或 ID。

---

## 二、物理分层

```text
system.dict          随软件发布，只读，系统升级覆盖
user_p.dict          P 域私人字典，读写，独立保险库
user_c.dict          C 域私人字典，读写，独立保险库
```

当前单文件版没有物理拆文件；保险库 payload 预留：

```json
{
  "systemVersion": "2026.11.1",
  "dictSourceP": "...",
  "dictSourceC": "...",
  "anchors": [],
  "legacyDictSource": "..."
}
```

- `system.dict` 的校验和写进 `systemVersion`；升级只替换母树，不碰用户文件。
- `user_p.dict` 与 `user_c.dict` 不共享节点 ID、别名、简码。
- 同一个「星巴克」在 P、C 各建一次，就是两个不同 ID；报表不互相抵扣。
- 旧 `dict.tv` 只迁移到 P；C 需要用户显式建立。

## 三、数据模型

### 3.1 母树节点

```text
SystemNode {
  id:        "SYS.ACC.EXPENSE"        // 稳定语义 ID，永久不复用
  kind:      "account" | "tag" | "behavior" | "merchant"
  zh_name / en_name
  parent_id: "SYS.ACC" | null         // 母树内部层级
  type:      "费用" | "资产" | ...    // 会计大类，只读
  version:   "2026.11.1"
  aliases:   ["餐饮", "dining", "吃饭"]
}
```

约束：

1. 母树 ID 是语义 ID，不是随机 ID，也不是名字。
2. 母树节点只读；用户不能改母树的名字、极性、父子关系。
3. 母树的父子关系必须无环；深度建议不超过 4。
4. 母树只提供分类与极性，不提供余额、不参与平账。

### 3.2 私人节点

```text
UserNode {
  id:         "N_ab12cd34"           // 现有随机 ID，保持不变
  domain:     "P" | "C"              // 物理隔离
  zh_name / en_name / zh_code / en_code
  parent_id:  "N_..." | null         // 私人树内部层级
  anchor_id:  "SYS.CAT.DINING" | null // 公共归属；跨域唯一
  weight, aliases, system
}
```

关键区分：

| 字段 | 含义 | 谁决定 |
|---|---|---|
| `parent_id` | 私人树里的父节点 | 用户 |
| `anchor_id` | 公共母树里的归属 | 用户确认，系统建议 |
| `type` / `polarity` | 会计大类与 A/B 极 | 默认继承 `anchor_id`，用户不能随意改 |

`parent_id` 与 `anchor_id` 不是一个东西：

- 私人树可以按用户习惯组织（例如「吃喝」下放「咖啡」）；
- 公共归属只决定报表向上合并到哪个标准类；
- 两者不一致是合法的，但 UI 必须同时展示，不能假装它们是同一层。

### 3.3 锚定不变量

1. `anchor_id` 必须指向母树节点；不能指向私人节点。
2. 一个私人节点最多一个 `anchor_id`。
3. 私人的 `type` 默认从锚点继承；若锚点是 `费用`，私人节点不能静默变成 `资产`。
4. 跨域不锚定：P 节点不能锚到 C 节点，反之亦然；母树没有域。
5. 母树节点不能有 `anchor_id`，不能出现在用户字典的写路径。
6. 删除/升级母树节点时，旧 `anchor_id` 保留在用户文件中并标记 `stale_anchor`，不静默改挂。

## 四、字典语法

### 4.1 母树（随软件发布，用户不看）

```text
[System.会计大类]
SYS.ACC.EXPENSE  | 费用 | Expense | A
SYS.ACC.ASSET    | 资产 | Asset   | A

[System.场景簇]
SYS.CAT.DINING   | 餐饮 | Dining | @SYS.ACC.EXPENSE
SYS.CAT.COFFEE   | 咖啡 | Coffee | @SYS.CAT.DINING
SYS.CAT.TAKEOUT  | 外卖 | Takeout | @SYS.CAT.DINING

[System.商户]
SYS.MERCHANT.STARBUCKS | 星巴克 | Starbucks | @SYS.CAT.COFFEE
```

### 4.2 私人子树

```text
[P.资产]
我的微信 | MyWeChat | wx @SYS.ACC.ASSET

[P.费用]
星巴克 | Starbucks | sbk @SYS.CAT.COFFEE
美团外卖 | MT_Takeout | mt @SYS.CAT.TAKEOUT
```

- `@` 后只允许 **母树稳定 ID**；当前旧语法里的私人 `@父码` 继续兼容，但新写入必须写母树 ID。
- 没有 `@` 的私人节点合法，进入 `未归类`；系统不得擅自猜一个归属。
- 同一简码在 P/C 各自解析；跨域必须写 `P:` / `C:` 前缀。

## 五、本地模型如何生成层级

结论：**可以，但模型只能提出「候选归属」，不能直接改数据。**

### 5.1 四段流水线

```text
原始商户/备注文本
  ↓ 清洗：去门店后缀、订单号、日期、支付方式、空格
  ↓ 第一阶段：确定性匹配（母树别名 / 私人历史 / 精确 code）
  ↓ 第二阶段：本地嵌入最近邻（可选）
  ↓ 第三阶段：本地小模型受约束分类（只从候选 ID 中选）
  ↓ 第四阶段：置信度 + 用户确认
  ↓ 写入 user_*.dict 的 anchor_id
```

### 5.2 推荐实现

| 层 | 建议 | 说明 |
|---|---|---|
| 清洗 | 纯 JS 规则 | 去掉「美团外卖-xx店」「订单 123」等噪声 |
| 精确匹配 | 母树 aliases + 私人 aliases | 命中即结束，不调用模型 |
| 向量召回 | 本地 `bge-small-zh` / `nomic-embed-text` | 只召回 top-k，不是最终裁决 |
| 生成裁决 | Ollama 运行 `qwen2.5:3b` 或 `llama3.2:3b`（4-bit） | 输入只含候选词与候选 ID 列表 |
| 结构化输出 | JSON Schema / grammar 约束 | 只允许 `system_id`, `confidence`, `reason` |
| 缓存 | 以「规范化词 + systemVersion」为键 | 同一个词不重复推理 |

模型输入示例：

```json
{
  "token": "星巴克",
  "candidates": [
    {"id": "SYS.CAT.COFFEE", "path": "费用/餐饮/咖啡"},
    {"id": "SYS.CAT.TAKEOUT", "path": "费用/餐饮/外卖"},
    {"id": "SYS.CAT.TRANSPORT", "path": "费用/交通"}
  ]
}
```

模型输出只接受：

```json
{"system_id": "SYS.CAT.COFFEE", "confidence": 0.91, "reason": "咖啡商户"}
```

### 5.3 置信度策略

| 置信度 | 行为 |
|---|---|
| `>= 0.85` | 气泡建议，默认高亮；仍需用户一次确认 |
| `0.60–0.85` | 展示 2–3 个候选，让用户选 |
| `< 0.60` | 进入「未归类」，不弹强制选择 |

**永不自动写入 `anchor_id`。** 用户点「采纳」才写入；忽略则记住 `ignored`，不再重复打扰。

### 5.4 为什么不让模型直接生成层级

- 小模型会编造不存在的母树 ID；
- 同一商户在不同上下文可能属于不同类；
- 自动改账会破坏可复现性；
- 本地模型应该做「排序与建议」，不是「事实来源」。

母树是事实来源；模型是推荐器；用户是裁决者。

## 六、报表合并

报表保留两个视角：

```text
私人视图：我的微信 → 星巴克 → 美团外卖（明细）
公共视图：费用 → 餐饮 → 咖啡 / 外卖（按 anchor 汇总）
```

规则：

1. 明细永远按私人节点展示，不把用户的「星巴克」改名为「咖啡」。
2. 公共汇总沿 `anchor_id` 的母树祖先链向上合并。
3. 一个节点只能计入一条祖先链；不允许重复计数。
4. `anchor_id = null` 统一进「未归类」，不偷偷塞进「其他」。
5. `stale_anchor` 单独显示警告，不计入公共汇总，直到用户重新确认。
6. 跨域转账仍按现有 `crossNetDelta` 处理；母树汇总不改变平账等式。

## 七、UI 文案

私人字典视图：

```text
[费用]
sbk  星巴克      归属：餐饮 / 咖啡
mt   美团外卖    归属：餐饮 / 外卖
```

点击「归属」打开小卡片：

> 这是系统公共母树的分类。所有归入此项的私人消费，会在合并报表中统计到【餐饮】。
> 你可以随时更改归属，或改为「未归类」。

建议气泡：

> 发现新词「星巴克」。母树建议归入【餐饮 / 咖啡】。
> [采纳] [换一个] [暂不归类]

- 不显示母树 ID；
- 不显示后台随机 ID；
- 不自动创建节点；
- 采纳后才写入 `user_p.dict` / `user_c.dict`。

## 八、迁移

1. 保留现有 `N_*` / `T_*` / `H_*` ID，不重新生成。
2. 旧 `dict.tv` 全量迁入 `user_p.dict`；C 域节点若存在，迁入 `user_c.dict`。
3. 所有旧节点 `anchor_id = null`，先进入「未归类」。
4. 提供一次性「批量建议」：只生成建议，不自动写。
5. 旧 `@父码` 继续解析为私人 `parent_id`；不自动升级为母树锚点。
6. 用户确认后，才写 `anchor_id` 与 `systemVersion`。

---

## 九、验收

- [ ] 母树只读，用户编辑无法写入母树；
- [ ] P/C 节点 ID 不共享，别名不串域；
- [ ] 一个私人节点最多一个锚点，锚点必须是母树；
- [ ] 未确认的建议不写 `anchor_id`；
- [ ] 删除/升级母树节点时不静默改挂；
- [ ] 报表明细与公共汇总都能复现；
- [ ] 未归类不被偷偷合并；
- [ ] 旧账本迁移后金额、余额、事件数不变；
- [ ] 模型不可用时，确定性匹配与手动归属仍然完整可用。

---

## 十、非目标

- 不让模型自动创建母树节点；
- 不让模型直接改私人树；
- 不把母树当余额账户；
- 不做云端同步；
- 不把「归属」和「私人父子」混成同一个字段。
