# 母树的双语与简码模型

> 状态：**已落地到 `system.dict`**（推荐码内联在 `[Tree]` / `[Merchant]` 行；
> 首版 190 节点 / 162 叶子 / 56 银行 / 30 商户；`tests/system-i18n.test.cjs` 全过）。
>
> 结论：**“一组一组”是对的，但一组不是两个节点。**
> 一组 = **一个母树顶点 + 一对名称（中/英）+ 一对推荐简码（可选）**。
> 简码的权威放在**私人树**；母树只给推荐值，不把简码当身份。

---

## 一、先定三条

1. **语言是标签，不是节点，也不是域。**
   中文名、英文名是同一个顶点的两个 label；切换语言不改变树、ID、锚点、汇总。
2. **一个概念一个顶点。**
   不建“中文咖啡节点”和“英文咖啡节点”两个顶点。
3. **简码是私人输入层的标识。**
   母树可以有“推荐简码”，但真正用于流水/投影的 `zh_code` / `en_code`
   属于私人节点；P/C 各自唯一。

---

## 二、为什么不能建两个节点

如果做成：

```text
SYS.CAT.DINING.COFFEE.ZH   咖啡茶饮
SYS.CAT.DINING.COFFEE.EN   Coffee
```

会同时破坏四件事：

| 问题 | 后果 |
|---|---|
| 图论 | 同一概念变成两个顶点，层叠集合不再“一个概念一个原子” |
| 汇总 | 私人节点锚到中文节点，英文报表就漏；锚到英文节点，中文报表就漏 |
| 锚点 | 一个私人节点最多一个锚点，必须在两个“同义节点”里二选一 |
| 维护 | 改名、改父级、加别名都要改两份，容易漂移 |

正确做法：

```text
SYS.CAT.DINING.COFFEE
  labels: { zh: "咖啡茶饮", en: "Coffee" }
  codes:  { zh: "cof",      en: "coffee" }   // 推荐，不是身份
```

一个顶点，两个 label。树不变，语言切换只换显示。

---

## 三、三种方案对比

| 方案 | 身份 | 简码权威 | 优点 | 问题 |
|---|---|---|---|---|
| A. 双语双节点 | 中文节点 + 英文节点 | 各自 | 看起来“成对” | 汇总重复、锚点二选一、维护两份 |
| B. 母树权威双语简码 | 一个节点 | 母树 | 输入统一 | 简码变成公共契约；P/C 冲突；用户不能改；升级要保码 |
| **C. 母树双语名称 + 推荐简码；私人树权威简码** | **一个节点** | **私人树** | 树稳定、简码可定制、P/C 不串、语言不影响树 | 需要在创建私人节点时做一次预填/查重 |

**推荐 C。**

理由：

- 母树是“公共语义目录”，不是“输入法词库”；
- 流水只引用私人节点，不直接引用母树节点，所以母树简码不是必需的；
- 私人简码需要按域查重、按用户习惯调整，放在母树会僵化；
- 母树给推荐简码，只是减少用户手填，不是承诺唯一。

## 四、数据结构

### 4.1 母树：`system.dict` 分区

```text
[Tree]        ID | 中文名 | 英文名 | @父ID | kind | 大类 | 中文推荐码 | 英文推荐码 | 权重 | 排序
[Alias]       ID | lang | 别名
[Merchant]    ID | 中文名 | 英文名 | default_category | 中文推荐码 | 英文推荐码 | 权重
```

例子：

```text
[Tree]
SYS.CAT.DINING.COFFEE | 咖啡茶饮 | Coffee | @SYS.CAT.DINING | category | - | cof | coffee | 90 | 10
SYS.CAT.DINING.GENERAL | 餐饮·未细分 | Dining General | @SYS.CAT.DINING | category | - | din_gen | din_gen | 60 | 99

[Alias]
SYS.CAT.DINING.COFFEE | zh | 咖啡
SYS.CAT.DINING.COFFEE | zh | 奶茶
SYS.CAT.DINING.COFFEE | en | coffee
SYS.CAT.DINING.COFFEE | en | latte

[Merchant]
SYS.MERCHANT.STARBUCKS | 星巴克 | Starbucks | SYS.CAT.DINING.COFFEE | sbk | starbucks | 80

[Alias]
SYS.MERCHANT.STARBUCKS | zh | 星巴克
SYS.MERCHANT.STARBUCKS | zh | 星巴克咖啡
SYS.MERCHANT.STARBUCKS | en | starbucks
SYS.MERCHANT.STARBUCKS | en | sbk
```

规则：

1. `[Tree]` / `[Merchant]` 的 `中文名`、`英文名` **都必须非空**；不允许只写一边。
2. 推荐简码写在 `[Tree]` / `[Merchant]` 行里，一组两码；叶子必须有中英两码，内部节点不写码。
3. `[Alias]` 按语言分开；同一语言内别名全树唯一。
4. 一个概念只有一个 `[Tree]` 行；不存在 `*.ZH` / `*.EN` 两个节点。
5. 母树推荐码在母树内按语言唯一；私人树仍可改，不把母树码当身份。
6. 母树推荐码不参与锚点、汇总、哈希里的“身份”；改推荐码不需要迁移用户数据。

### 4.2 私人树：简码在这里诞生

私人节点仍然是现在的一行：

```text
node P 费用 steam sbk starbucks 星巴克 | Starbucks 90 @cof ^SYS.CAT.DINING.COFFEE
```

- `zh_code` / `en_code` 是私人节点的**权威输入标识**；
- 同一域内唯一；P/C 可以各有一个 `coffee`；
- 创建时用母树推荐码预填，用户可以改；
- 如果用户只填中文简码，英文简码回退中文简码，并在 UI 标“英文简码未填”；
- 如果用户只填英文简码，中文简码同理回退并标记；
- 不自动翻译名字；缺英文名就回退中文名并标记，不假装有英文名。

### 4.3 一个完整例子

母树：

```text
[Tree]
SYS.CAT.DINING.COFFEE | 咖啡茶饮 | Coffee | @SYS.CAT.DINING | category | - | cof | coffee | 90 | 10
```

私人 P：

```text
node P 费用 steam sbk starbucks 星巴克 | Starbucks 90 - ^SYS.CAT.DINING.COFFEE
```

私人 C：

```text
node C 费用 steam kf coffee 咖啡 | Coffee 80 - ^SYS.CAT.DINING.COFFEE
```

- P 的简码是 `sbk` / `starbucks`；
- C 的简码是 `kf` / `coffee`；
- 两者可以不同，互不干扰；
- 两者都锚到 `SYS.CAT.DINING.COFFEE`；
- 公共报表合并到“费用 / 餐饮 / 咖啡茶饮”，但明细仍显示各自私人名字。

### 4.4 英文名 vs 英文简码

| 字段 | 写法 | 示例 | 用途 |
|---|---|---|---|
| `en_name` | **空格**，自然英文 | `Industrial and Commercial Bank of China` | 显示、搜索 |
| `en_code` | **下划线/连字符**，单 token | `icbc`、`credit_union` | 流水输入 |
| `[Alias]` 英文 | **下划线/连字符**，单 token | `fixed_asset` | 搜索/输入 |

不要用下划线连接英文名。原因：

- 英文名是给人看的自然语言，下划线会像标识符；
- 系统用 `|` 分隔中文名和英文名，英文名里的空格不会破坏解析；
- 流水输入按空格切 token，所以只有 **简码/输入别名** 需要单 token；
- 母树英文名可以有多词，私人节点英文名也可以有多词。

校验器会对含空格的英文别名给一条 `ALIAS_SPACE` 警告：
“只用于搜索；流水输入请用简码”。当前 `system.dict` 已无此警告。

## 五、创建私人节点时的流程

```text
用户搜索“咖啡”
  → 母树候选：费用 / 餐饮 / 咖啡茶饮
  → 选中叶子
  → 预填：
       zh_name = 咖啡茶饮
       en_name = Coffee
       zh_code = cof（推荐）
       en_code = coffee（推荐）
  → 域内查重：
       同域已有 cof/coffee？
         有 → 提示换一个，或自动加后缀（cof1/coffee1）
         没有 → 通过
  → 用户确认创建
  → 写私人节点；如果这次选择就是用户明确采纳，则写 anchor_id
```

**“未确认不写锚点”仍然成立：**

- 只是浏览母树、看建议 → 不写；
- 从母树选叶子并确认创建 → 这是一次明确选择，可以写锚点；
- 建议气泡点“采纳” → 明确确认，可以写；
- 点“换一个”“暂不归类” → 不写。

## 六、显示与输入

### 6.1 语言切换

`lang = zh | en` 只影响：

- `zh_name` / `en_name` 的显示；
- `zh_code` / `en_code` 的显示；
- 母树 `path(id, lang)` 的路径文字；
- 建议候选的主标题/副标题。

不影响：

- 节点 ID、父子关系、锚点、余额、汇总；
- 树的形状；
- 公共/私人报表的数字。

### 6.2 4 态投影

现有 4 态是“简码/明文 × 中/英”。
它使用的是**私人节点**的 `zh_code` / `en_code` / `zh_name` / `en_name`，
不是母树推荐码。母树推荐码只在创建时预填。

- 私人节点缺英文简码 → 英文态回退中文简码；
- 私人节点缺英文名 → 英文态回退中文名；
- UI 标“英文缺失”，不自动翻译。

### 6.3 搜索与输入解析

- 输入 `coffee`：先查私人同域 `en_code` / 英文别名；没有再查母树英文别名/推荐码，作为建议；
- 输入 `咖啡`：先查私人同域 `zh_code` / 中文别名；没有再查母树中文别名；
- 中英文都查，但**当前语言优先**；
- 候选列表同时显示中英文名，避免切语言后认不出；
- 母树推荐码不作为流水绑定目标，只用于建议/预填。

### 6.4 不显示母树 ID

友好界面只显示路径：

```text
中文：费用 / 餐饮 / 咖啡茶饮
英文：Expense / Dining / Coffee
```

不显示 `SYS.CAT.DINING.COFFEE`。
源码编辑器可以显示 `^SYS...`，那是高级视图。

## 七、图论不变量

在原来的 G1–G15 上，再加三条：

| 编号 | 条件 | 检查方法 |
|---|---|---|
| G16 | 一个概念一个顶点；不存在中英重复节点 | 统计 `zh_name` / `en_name` 组合；不允许 `*.ZH` / `*.EN` |
| G17 | 每个 `[Tree]` / `[Merchant]` 节点中英文名都非空 | 解析时校验 |
| G18 | 语言切换不改变树、锚点、报表 | 同一账本切 `zh/en`，节点数/边数/锚点数/汇总数完全相等 |
| G19 | 私人简码按域唯一，P/C 可同码 | 编译时 `seen[kind][domain]` |
| G20 | 母树推荐码不是身份 | 改推荐码不改变节点 ID、不改变锚点、不改变哈希 |

形式化地说：

> 语言是一个**标签函数** `label: V → {zh, en}`；
> 它不增加顶点、不增加边，也不改变 `parent_id`。
> 简码是私人顶点的属性，不是母树的边或身份。

## 九、结论

- **一组一组**：一个母树顶点 + 一对名称 + 一对推荐简码 + 分语言别名。
- **不建两个节点**：中英是同一顶点的两个标签；两个节点会破坏层叠树和汇总。
- **简码在私人树才成为权威**：母树只给推荐值；私人树按域查重、可改、可回退。
- **语言不是域**：P/C 是账本域；zh/en 是显示语言，两者正交。
- **图论上**：语言是标签函数，不增加顶点/边；G1–G15 不变，新增 G16–G20。

这样既能双语显示、双语简码，又不会把母树变成两套重复的树。
